ALambda File To Files — 许可与合规说明
=======================================

本文档说明三件事：
  1. 本程序分发了哪些第三方软件、各自是什么许可；
  2. 因此需要履行哪些义务；
  3. 商用与开源时需要注意什么。

【重要】本文档是工程层面的合规梳理，不构成法律意见。
正式商业发行前，建议咨询熟悉开源许可与专利的律师。

二、内置的 FFmpeg
--------------------------------------------------------------------------------
本程序随包分发以下 FFmpeg 可执行文件：
    ffmpeg\ffmpeg.exe       转码
    ffmpeg\ffprobe.exe      媒体信息探测

版本：n9.0.2-36-g6882969ce9-20261026（2026-10-26 构建）
来源：gyan.dev 的 win64-gpl 构建
许可：GNU General Public License v3
      （构建参数含 --enable-gpl --enable-version3）

为什么是 GPLv3 而不是更宽松的 LGPL：
    为了支持 H.264 / H.265 编码，构建中启用了 libx264、libx265、libxvid，
    这三个库是 GPL 许可，因此整个 FFmpeg 二进制必须以 GPLv3 分发。
    若换成 LGPL 构建，就无法提供 H.264 / H.265 编码——而这是本软件的核心功能。

--------------------------------------------------------------------------------
三、分发 FFmpeg 时必须履行的 GPLv3 义务
--------------------------------------------------------------------------------
1. 随包附上完整许可证文本 —— 已包含：ffmpeg\LICENSE.txt
2. 保留版权声明与作者署名 —— 已包含在二进制与许可证中
3. 提供“对应源码”（Corresponding Source），即构建该二进制所用的确切源码，
   或提供等价获取方式（GPLv3 第 6 条）。本程序采用两种方式叠加：
        - 在 SOURCE-OFFER.txt 中写明具体版本、提交号、构建脚本与获取地址；
        - 同时给出三年有效期的书面承诺，任何人可索取源码副本。
4. 不得对 FFmpeg 部分附加额外限制（例如禁止逆向工程、限制再分发）。
5. 若修改过 FFmpeg 源码，必须标注修改、并以 GPLv3 发布修改部分。
   本程序未修改 FFmpeg 源码，仅以命令行方式调用。

--------------------------------------------------------------------------------
四、本程序与 FFmpeg 的关系（程序聚合）
--------------------------------------------------------------------------------
本程序：
    - 不链接 FFmpeg 的任何库（无静态/动态链接）；
    - 不修改 FFmpeg 源码；
    - 运行时创建独立进程，用命令行参数调用 ffmpeg.exe / ffprobe.exe，
      通过标准输出与标准错误读取进度和结果。

按照 FSF 对 GPL 的官方解释（GPL FAQ "MereAggregation"），
通过命令行参数、管道等通用机制通信的独立程序，通常被视为“聚合”而非衍生作品，
因此本项目自身的代码不必以 GPL 发布。

【提醒】这是一个存在解释空间的边界问题。如果发行方式发生变化，例如：
    - 改为静态链接 libav* / libavcodec；
    - 把 FFmpeg 编译进主程序；
    - 通过共享内存、COM 组件等方式深度集成；
整体就可能被认定为“单一作品”，从而必须整体以 GPL 发布。
做这类改动之前请先评估，必要时咨询律师。

--------------------------------------------------------------------------------
五、编解码器的专利风险（与开源许可无关，但商用必须了解）
--------------------------------------------------------------------------------
开源许可只解决“版权”，不解决“专利”。
FFmpeg、x264、x265 本身都不授予任何专利许可。部分格式涉及专利池：

    格式          专利状况（截至 2026 年，仅供参考）        商用风险
    ----------    --------------------------------------    ----------------
    H.264 / AVC   专利池仍在收费（Via LA 等）                中高，需评估
    H.265 / HEVC  多个专利池（Access Advance / Via LA 等）   中高，需评估
    AAC           涉及专利许可                              中
    MP3           核心专利已全部到期                         低
    VP9           Google 主张免费                            低
    AV1           AOMedia 免专利（含防御性条款）              低
    Opus / Vorbis 免专利                                     低
    FLAC / PCM    免专利                                     低

结论：
    - 个人使用、免费开源分发：通常无需处理专利问题（专利池一般不针对非商业用途）。
    - 商业发行（售卖软件、硬件捆绑、企业批量分发）：
      H.264 / H.265 / AAC 相关功能可能需要向相应专利池取得许可。
      规避思路：默认只提供免专利格式（AV1 / VP9 / Opus / FLAC），
      或由发行方自行取得专利许可。

--------------------------------------------------------------------------------
六、为什么选择 MIT（以及曾经考虑过的方案）
--------------------------------------------------------------------------------
本项目最终选择 MIT：允许任何人自由使用与修改，商用与闭源再分发也不需要额外授权，
只需要保留版权声明。对本项目而言，MIT 的简洁性比专利条款更重要。

下面保留当初的对比，方便日后需要重新评估时参考：

--------------------------------------------------------------------------------
    协议          传染性   可商用   专利条款              适合场景
    ----------    ------   ------   -------------------   ---------------------------
    MIT           无       可以     无                    希望别人随便用，包括闭源商用
    Apache-2.0    无       可以     有（明确授权+报复条款） 商用友好且更稳妥
    GPLv3         强       可以     有（明确）             希望衍生作品也开源
    AGPLv3        极强     可以     有                    提供网络服务也要求开源

当前选择：MIT。

如果将来改变主意：
    * 想更强调专利授权与免责 → 可考虑 Apache-2.0。
    * 想让衍生作品也开源     → 可考虑 GPLv3（与分发 GPL FFmpeg 行为最一致）。
    * 不建议 AGPL（除非做成在线服务），也不建议 BSL/SSPL 这类非 OSI 协议。

注意：开源协议一旦发布不可撤回。
      你可以用新协议发布后续版本，但已经按旧协议发布的版本仍然有效。
